#  博客系统设计（含搜索系统）

##  项目目标

设计并实现一个博客系统，支持多类型内容展示，并具备关键词搜索、模糊搜索与推荐功能。

---

#  一、整体架构设计

系统采用如下设计思想：

- 分类（Category）与内容类型（Type）解耦
- Markdown 文件存储文章主体内容
- 数据库存储元信息与索引字段
- 前端基于 Vue3 动态组件渲染不同类型内容

---

#  二、数据库设计

## 1. 文章表（post）

```sql
post
--------
id
slug            -- URL 段，唯一约束；对外路由如 /blog/:slug
title           -- 标题
md_url          -- 原始 Markdown 文件在服务端的内容路径/定位（见「实施决议」）
summary         -- 摘要
keywords        -- JSON 数组（关键词）
category_id     -- 分类 ID（与 type 严格对应，不允许错配）
type            -- 内容类型，存整型：0=article，1=project，2=algorithm
views           -- 浏览量（用于推荐排序）
created_at
```

> 字段以「十一、实施决议」为准；`slug` 与 `type` 整型为实施阶段补充。

---

## 2. 分类表（category）

```sql
category
--------
id
name        -- 分类名称（杂项 / 项目 / 算法）
parent_id   -- 父分类（可扩展）
```

#  四、搜索系统设计

---

## 1. 基础搜索

支持字段：

- 标题（title）
- 摘要（summary）
- 关键词（keywords）

SQL 示例：

```sql
WHERE
  title LIKE '%keyword%'
  OR summary LIKE '%keyword%'
  OR JSON_CONTAINS(keywords, '"keyword"')
```

---

## 2. 模糊搜索

### 方案：关键词拆分

输入：

```text
vue jwt
```

处理：

```text
["vue", "jwt"]
```

**已定方案（方案 C，详见第十一节）**：对**每个**搜索词，要求在该词的匹配中，**title、summary、keywords 至少其一命中**（字段之间为 OR）；**多个词之间为 AND**（每个词都要满足一次「三字段之一命中」）。不在此使用「仅 title 多 AND」的简化 SQL。

---

## 3. 排序策略（核心）

评分规则（概念权重；**最终 score 在后端按词计算**，见第十一节）：

```text
标题匹配      +10（每个词、每个字段至多计一次）
关键词匹配    +6
摘要匹配      +3
浏览量加权    +log(views + 1)
```

排序：按计算得到的 `score` **降序**（实现上在应用层排序，而非纯 SQL `ORDER BY score`）。

#  五、推荐系统设计

---

## 1. 推荐逻辑

基于关键词相似度：

```text
关键词重合数量越多 → 越相关
```

---

## 2. 示例

当前文章：

```json
["vue3", "jwt", "权限"]
```

推荐：

```text
计算与其他文章 keywords 的交集数量
```

---

## 3. 推荐算法（伪代码）

```js
score = intersection(post.keywords, current.keywords).length
```

排序规则：

```text
优先关键词重合
其次浏览量
```

# 十一、实施决议（补充）

以下条目来自设计与实现前的约定，作为开发时的**单一事实来源**；若与前文示例 SQL 冲突，以本节为准。

## 1. 技术栈

- **数据库**：MySQL（可使用 `JSON` 类型存 `keywords`，查询时注意与版本兼容的 JSON 函数）。
- **后端**：**Python + Flask**，对外提供 **HTTP JSON API**。
- **前端**：Vue 3 站点**完全改为请求后端 API** 获取文章列表、详情、搜索与推荐；**不再**以静态 `posts.json` 等文件作为主数据源。

## 2. `md_url` 含义

- 表示该篇文章对应的 **原始 Markdown 文件在服务端侧的定位**（例如相对内容根目录的路径）。
- 由后端按约定路径 **读取文件内容**，再通过 API 提供给前端渲染；含义不是「必须由浏览器直接打开的公网 URL」，除非后续单独约定。

## 3. 分类（Category）与类型（Type）——严格对应

- **不允许**「类型与分类」错配：例如「项目类文章」必须属于「项目」分类；**杂项 / 项目 / 算法** 与 **article / project / algorithm** 一一对应。
- 在 `post.type` 中存储 **整型枚举**（**不要**存英文单词字符串）：
  - `0` → article（普通文章 / 杂项归档）
  - `1` → project（项目）
  - `2` → algorithm（算法）
- API 响应中可同时返回数字 `type` 与字符串别名（如 `type_name`），便于前端与文档一致。

## 4. `slug` 与路由

- 对外文章页路径采用 **`/blog/:slug`**。
- 数据库 **`post.slug`**：**全局唯一**（UNIQUE），**字符串**。
- **`id`**：自增主键，仅用于内部关联与稳定引用；对外展示与链接以 **`slug`** 为主。

## 5. 模糊搜索（方案 C）细则

- 用户输入经拆分为若干 **词**（如 `vue jwt` → `["vue","jwt"]`）。
- 对 **每一个词**，在 **title、summary、keywords** 中 **至少一个字段** 出现该词即视为该词命中（字段之间 **OR**）。
- **所有词均命中**时，该帖子才进入结果集（词之间 **AND**）。
- 实现上可先粗筛（如 SQL `LIKE` / JSON 包含）再在后端过滤，或由应用层组合条件；**不以**「多词全部仅在 title 上 AND」作为最终规则。

## 6. 评分与排序（后端计算）

- **不在数据库内**用纯 SQL 表达最终综合分；在 **Python 后端**对候选帖计算 `score` 再排序。
- **按「词」计分**：对每个搜索词，分别在 title / summary / keywords 中判断是否命中；**同一词在同一字段内无论出现多少次，该字段对该词只加一次对应分值**。
- 字段权重（与第四节一致）：标题 **+10** / 关键词 **+6** / 摘要 **+3**（按词、按字段去重后累加）。
- 浏览量项：**`log(views + 1)`**（避免 `views = 0` 时数学问题）。
- 返回列表按 **`score` 降序**；同分时可按 `views` 或 `created_at` 作为次要排序（实现时写明）。

## 7. API 范围

- **第一期仅提供只读 API**（查询文章、搜索、推荐、拉取 Markdown 内容等），**不包含**后台登录与文章 CRUD；数据通过迁移脚本、SQL 或种子文件导入。

## 8. 与本文档其他章节的衔接

- 第五节推荐：**关键词交集数量** 为主排序、**浏览量** 次之——保持不变；实现时注意与 `type` 整型、`slug` 字段一致。
- 第六节前端：Markdown 获取方式改为 **调用 Flask API**（如返回正文文本或带元数据的 JSON），由前端再解析为 HTML。
