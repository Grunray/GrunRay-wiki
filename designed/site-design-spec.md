# 个人成果站设计说明

> 本文档汇总站点的产品与信息架构约定，便于后续实现与修订。  
> 技术选型：**Vue 3（前端）** + **Python（后端/构建/校验等）**。

---

## 1. 站点定位

- **目标**：展示个人项目成果，并承载项目相关笔记、算法学习博文等内容。
- **原则**：**数据驱动、易于扩展、符合规范**；内容更新频繁时以「加数据而非改业务代码」为主。
- **访客路径（建议）**
  - 首页：一句话定位 + 精选项目 + 次要入口（关于、博客等）。
  - 项目列表：支持筛选/分类（标签、技术栈、年份等可逐步扩展）。
  - 项目详情：统一信息结构，允许不同项目采用不同展示块（见第 4 节）。

---

## 2. 内容类型


| 类型                          | 说明                                            |
| --------------------------- | --------------------------------------------- |
| **项目（Project）**             | 成果主体；支持归档与隐藏。                                 |
| **项目笔记（Project note）**      | **必须**关联某一项目；开发记录、迭代说明等。                      |
| **算法博文（Algorithm article）** | 独立内容；**不**绑定项目；使用**单独子 schema** 扩展字段（见第 6 节）。 |


---

## 3. 项目状态：归档与隐藏

建议语义分离，避免混用：


| 状态     | 含义（建议）                                    |
| ------ | ----------------------------------------- |
| **隐藏** | 公共列表不出现；详情与直连策略与项目一致（如统一 404）。            |
| **归档** | 可出现在「归档」筛选或折叠区域；详情仍可访问（产品层需统一是否打「已归档」角标）。 |


---

## 4. 媒体与展示：同一项目、多种展示方式

- **内容层**：正文以 Markdown（或最终落盘的结构化内容）为主；可用 frontmatter 描述段落角色，例如 `role` / `feature_key`（如 `overview`、`demo`、`changelog`、`gallery`）。
- **展示层**：项目详情页通过**配置或注册表**决定各块的顺序与布局组件（如图文横排、嵌入 Demo、图集瀑布流等）。  
**扩展方式**：新增一种展示 = 新增一种 **layout / block 类型**，而非为每个项目单独硬编码页面。

---

## 5. 博客与列表

### 5.1 需求摘要

- 项目笔记：需按项目拉取列表/详情的「接口」能力（与前端路由对应，如 `/projects/:slug/notes`）。
- 算法博文：独立系列与接口（如 `/algorithms` 或等价路径）。
- **统一博客视图**：一个可展示**全部**可公开笔记/文章的界面；底层为统一集合，通过过滤条件区分用途。

### 5.2 数据关系（概念）

- 底层可为统一 `posts` / `documents` 集合，用 `type` 区分 `project_note` 与 `algorithm`。
- `project_note` 必填 `**project_id`**（或稳定 slug 关联）；`algorithm` 不填项目关联。

### 5.3 列表排序规则（全局一致）

1. `**pinned === true` 的条目排在前面**。
2. 置顶组内：建议使用 `**pinned_order` 升序**（未填的可视为最大、排在置顶组末尾）；若简化实现，可退化为置顶组内按 `**published_at` 降序**。
3. 非置顶：按 `**published_at` 降序**（或全站统一改用 `updated_at`，二选一并写死）。

适用于：博客总览、算法列表、某项目下的笔记列表（除非某页产品明确要求不同顺序）。

## 6. Schema 分层

### 6.1 文章类共用基底（示例字段）

以下适用于项目笔记与算法博文（具体命名实现时可映射为 JSON/YAML 字段）：

- `id`、`slug`
- `locale`（为**国际化预留**，如 `zh` / `en`）
- `title`、`summary`
- `published_at`、`updated_at`
- `tags`
- `pinned`、`pinned_order`（可选）
- `type`：`project_note` | `algorithm`
- 封面与媒体引用（按实现细化）

**国际化（预留）**

- 推荐：每篇带 `locale`；同一主题多语言稿用 `translation_of` 或 `canonical_id` 关联。  
- 或：同 slug 下分文件 `content.zh.md` / `content.en.md`。  
- 界面文案与正文分开管理（Vue i18n 与内容仓库分离）。

### 6.2 项目笔记扩展

- `**project_id`（必填）**，否则校验失败。
- 可选：`role` / `feature_key`，用于项目详情页多块展示。

### 6.3 算法子类型扩展（独立 schema）

- 仅在 `type === algorithm` 时校验与填写，例如（可按需增删）：
  - `difficulty`
  - `oj`、`problem_id`
  - `series`（系列名）
  - 其他算法笔记专有字段

项目笔记**不要求**包含上述算法专有字段。

---

## 7. 可见性规则

**已确认：笔记跟随项目可见性。**


| 项目状态 | 笔记在公开列表 / 聚合博客中的行为（建议）                  |
| ---- | --------------------------------------- |
| 正常公开 | 笔记若未单独隐藏，则随项目可被展示。                      |
| 归档   | 笔记可出现；建议 UI 标明所属项目已归档，或与「归档」筛选策略一致。     |
| 隐藏   | **笔记不进入任何公开列表**；详情行为与项目一致（推荐与项目同为不可访问）。 |


> 例外「项目隐藏但某篇笔记单独公开」当前**不采用**，避免与「跟项目走」冲突；若未来需要再单开规则。

---

## 8. 后端（Python）角色（概念）

- 内容以**仓库内文件**为主（如项目目录 + Markdown/frontmatter）时，Python 可负责：
  - **Schema 校验**（基底 + 子类型）
  - **生成索引**（供前端构建时拉取或运行时 API）
  - 未来：表单、统计、搜索索引等动态能力
- 前端 Vue：**只依赖 API 或构建期注入的 JSON 结构**，与具体文件布局解耦。

---

## 9. 全局壳层功能（与内容解耦）

以下属于「站点壳层」，建议可配置、可关闭（尤其动效），避免影响严肃内容阅读：

- **三档 UI 主题**：浅色 / 深色 / 抽象（见第 10 节：控制模块、令牌文件与职责拆分）。
- 鼠标光标拖尾等动效（建议与主题解耦为可单独关闭的开关，并尊重无障碍设置）。
- 无障碍：如「减少动效」与系统 `prefers-reduced-motion` 对齐。

---

## 10. 主题与 UI 令牌（三档模式）

### 10.1 模式定义

站点提供三种互斥的界面风格（实现时枚举建议稳定命名为 `light` | `dark` | `abstract`）：

| 模式 | 说明 |
|------|------|
| **浅色** | 常规浅色背景与对比度。 |
| **深色** | 常规深色背景与对比度。 |
| **抽象** | 独立视觉体系；**允许**在壳层或特定区域启用额外交互/装饰能力（与纯换色区分，见 10.4）。 |

用户通过 **滑动控件** 在三档之间切换（区别于常见的双色开关）。实现时需注意 **可访问性**：键盘可操作、当前选项可被读屏理解（如适当的 `aria-*`）、文案语义清晰。

### 10.2 文件职责拆分（推荐）

与业界常见的「设计令牌（Design Tokens）+ 根级主题状态」一致，建议拆为：

1. **UI 控制模块（单一文件或模块）**  
   - 维护**当前模式**（如根节点 `data-theme` / `class`）。  
   - 持久化键名建议固定（如 `localStorage`：`theme` 或 `ui.theme`）。  
   - 可选：是否与系统 `prefers-color-scheme` 联动；若联动，需约定与「抽象」档的优先级。  
   - **不存放**具体颜色十六进制；仅消费「当前是哪一种模式」。

2. **三套主题令牌文件（每模式一份）**  
   - 每文件只存放**视觉令牌**（色值、必要时含圆角/阴影等静态视觉参数）。  
   - 书写形式示例：`background: #FFDE09`，或更推荐映射为 **CSS 自定义属性**，如 `--color-bg-surface: #FFDE09`，组件与布局只引用语义变量名。  
   - 三套文件的 **语义键集合建议一致**，避免某一模式缺键导致回退不可预期；若抽象模式独有变量，须在文档或注释中标明「仅 `abstract` 使用」。

### 10.3 落地形式（实现阶段可选用其一）

- **CSS 变量表**：按 `[data-theme="light"]` / `dark` / `abstract` 分块定义变量，构建时合并或按需注入。  
- **JSON / TS 常量**：构建或运行时将令牌写入 `document.documentElement` 的样式（便于与设计工具导出对接）。

### 10.4 「抽象」模式与额外功能

- **颜色与静态视觉**：归入抽象主题令牌文件。  
- **新增交互、组件或布局差异**：由 **UI 控制模块** 根据 `theme === abstract`（或与独立 **feature 开关** 组合）驱动；**避免**在令牌文件内写业务分支，以免主题数据与逻辑耦合、难以测试与扩展。

### 10.5 与动效开关的关系

光标拖尾等属于 **壳层动效**，建议：

- 支持全局关闭；  
- 若「抽象模式下默认开启」等规则存在，可在控制逻辑中实现；**令牌文件仍以颜色/静态视觉为主**；动效强度可用独立令牌（如透明度）或独立配置项表达。
